# Component API: Builder chains at the core, function components, and props structs

The core view API uses ordinary Rust Builder chaining. Handwritten Builders retain native IDE completion, type checking and diagnostics. Macro syntax must expand to Builder calls and remain optional.

Components are functions: `fn(props) -> impl View`, executed only once at mount time (ADR-0005). Props are ordinary structs with Builders generated by a derive macro; event handlers use a common `Callback` type.

## Considered Options

- **Macro DSL first** (rsx! / view!): concise, but worse completion and diagnostics inside macros; reduced to optional syntax sugar.
- **External DSL files** (Slint style): strong static optimization, but requires switching between two languages and maintaining another compiler and LSP; rejected.
- **Trait components**: closer to OOP widgets, but mismatched with the execute-once, signal-driven component model.

## Consequences

- Control generic nesting depth in Builder types, for example by erasing types at child-node boundaries, to avoid compilation slowdowns from deeply typed view trees.
- Every macro expression must have directly equivalent Builder code.

## M3 implementation

`oxiview-macros` implements JSX-like `view!` expressions inside Rust
`.rs` files. A `<Node>` tag expands to `node()`, its attributes to Builder
methods and its children to `.child(...)`. Component tags call Rust functions
and accept a props expression. The `Props` derive generates a Builder for a
named props struct. The [Snake UI](../../examples/snake/src/application.rs)
uses this syntax. Standalone `.oxi` source files and a compiler for them
remain outside this design.

M3+1 adds optional external source syntax under
[ADR-0037](0037-optional-precompiled-oxi.md). The Builder and function-component
contracts above also govern that syntax.
