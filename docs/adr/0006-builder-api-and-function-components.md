# Component API: Builder chains at the core, function components, and props structs

The core view API is ordinary Rust Builder chaining, such as `v_stack().gap(8.0).child(text(name))`. IDE completion, type checking, and diagnostics retain the native Rust experience without macro compilation costs. Macros are only syntax sugar and must expand to Builder calls. A JSX-like `view!` macro may follow, but it remains an optional layer over Builders, never a mandatory dependency.

Components are functions: `fn(props) -> impl View`, executed only once at mount time (ADR-0005). Props are ordinary structs with Builders generated by a derive macro; event handlers use a common `Callback` type.

## Considered Options

- **Macro DSL first** (rsx! / view!): concise, but worse completion and diagnostics inside macros; reduced to optional syntax sugar.
- **External DSL files** (Slint style): strong static optimization, but requires switching between two languages and maintaining another compiler and LSP; rejected.
- **Trait components**: closer to OOP widgets, but mismatched with the execute-once, signal-driven component model.

## Consequences

- Control generic nesting depth in Builder types, for example by erasing types at child-node boundaries, to avoid compilation slowdowns from deeply typed view trees.
- A future JSX-like macro must preserve a one-to-one mapping: every macro expression has directly equivalent Builder code.
